# Architecture

The default entry on localhost:3000 immediately opens the Ultraviolet launcher on localhost:3001. Its worker controls /uv-service/. A saved encoded page link can bootstrap that worker in place. Pages render directly in the user's browser; there is no outer iframe, remote browser, public tunnel, browser extension or system proxy.

## Navigation and resource transport

Ultraviolet 3.2.10 rewrites navigation and executable URL operations. Asset/API URLs retain their original merchant/CDN origins. The controlling worker intercepts those cross-origin subresource requests, maps them internally into Ultraviolet's request context, and relays them through Node. Request destinations are preserved when creating that internal request. This lets the original CSP source list apply to the original resource URLs while the address bar remains localhost.

CSP response headers, including report-only policies, are restored unchanged after the engine. Local helpers are inserted inline; policies that do not permit those helpers may remain incompatible. Script nodes receive correct HTML namespaces/parent links so the serializer does not turn JavaScript operators into HTML entities.

UV's default renaming of integrity, nonce, crossorigin, sandbox and http-equiv attributes is reversed for markup and disabled for client attribute operations. Resources with Request.integrity are returned with their original bytes, bypassing content rewriting. The original hash stays in the document; no replacement hash is generated. Owned browser tests confirm both a valid hash executing and an invalid hash remaining blocked. External stylesheets retain original URLs and bytes so their relative resources resolve normally. CSP meta documents remain conservatively unsupported in the Node guard.

The owned CSP test uses fixture.temby.invalid, which has no upstream server, and a CSP that excludes localhost resources. Its original-origin protected script and API fetch pass through the worker/relay; this demonstrates the resource route rather than direct internet loading. Broad site compatibility is not established.

## Header and cookie fidelity

The critical original loop bug was an overly narrow request-header whitelist. It discarded opaque verification headers generated by the actual merchant script. The relay now preserves valid end-to-end header values unchanged. It blocks host overrides, hop-by-hop and connection-nominated headers, forwarded identity headers, authorization and internal fields. User-Agent is the real browser's value. Origin/Referer are validated virtual merchant URLs. Browser localhost session cookies are not forwarded as virtual cookies.

Response cookies are processed before body compatibility checks. Fetch/XHR HTML remains data and is not rejected simply because its text contains CSP/SRI declarations. Document-policy detection parses actual HTML attributes rather than matching JavaScript text. These fixes changed the observed verification response from roughly 2.9 KB to hundreds of KB of real HTML.

Server cookies use isolated tough-cookie jars. Virtual cookies merge with them while server HttpOnly values win; HttpOnly values are excluded from injected initialization. A cookie-write queue prevents UV's asynchronous browser persistence from racing immediate requests/navigation. Complete SameSite, logout/deletion, browser restart, worker termination and authenticated continuity remain unaudited.

Both page and worker use the custom transport. Leaving the page on default BareMux could require unconfigured browser state and fail fresh-profile initialization. No BareMux server/worker is needed in this implementation.

## Boundaries and unresolved behavior

Exact HTTPS hosts are www.temu.com, temu.com, static.kwcdn.com, img.kwcdn.com, aimg.kwcdn.com and eu.pftk.temu.com. The last two were observed in real page traffic and their DNS answers reviewed; no wildcard was added. DNS answers are revalidated at connection time and private addresses are rejected. TLS remains verified. Requests are bounded to 1 MiB and decoded responses to 12 MiB. Redirect destinations are checked. The owned fixture is answered in process without DNS/network access.

The latest real run loaded substantial page/vendor code and received API JSON, then actual upstream 403/429 responses and a verification navigation. Subsequent merchant transport remains halted; the original error response is preserved for the application. This is evidence of specific failed requests, not proof that every proxy architecture is impossible. No new live requests were made after that denial/rate limit. The newly observed host additions have not been live-retested.

The active relay no longer applies endpoint-name login/order filters or a session-wide denial latch. It forwards normal requests and upstream errors; per-method/URL 429 cooldowns preserve the original response and Retry-After without stopping unrelated requests. Full login/purchase behavior remains unverified. WebSockets and merchant workers remain unsupported. The old Scramjet and transport-only paths are diagnostics, not equivalent alternatives to the default flow.

Diagnostic events contain bounded host/method/status/type/size/destination/cookie-count metadata. Opaque custom header names and all header values, response bodies, cookie values and query strings are excluded. Runtime logging accepts only phase/error-class enums.

No verified Temu cart schema is implemented; real values stay unknown. Synthetic data stays separate. The original CSP header and integrity checks are preserved, but full virtual-origin security equivalence and production isolation require audit. A usable merchant shopping flow and commercial suitability remain unestablished.
